## Patterns

1. **Public claims are small product systems, not copy edits.** The parity
   phrase required fresh validation (R-031/T-052), multi-surface propagation
   (R-032/T-049), a CI guard (T-050), and an agent-admission policy (D-031/R-034).
   The team still starts by treating wording as cheap, then discovers the
   machinery the wording needs to remain true.

2. **Evidence records are becoming first-class launch infrastructure.** D-029
   preserved the degradation spike instead of deleting it; R-033 constrained the
   reframe so raw observations stayed intact; T-048 kept the old findings and
   repointed references; T-052 added a fresh dated validation layer. This is a
   strength: the project is learning to ship claims with evidence attached.

3. **Soft norms keep needing structure before they are real.** D-031's support
   bar needed T-051/T-050 to become checkable; D-032's rationale-first rule
   needed T-053's numbered checkpoint and example; R-035 and R-036 preserve the
   residual subjectivity. A prose rule is a starting point, not the control.

4. **The planning record is getting better at showing scars instead of sanding
   them away.** T-043 records a dropped publish task with the trade-off intact;
   T-048 records anchor drift after the fact; R-035 accepts a weak pass
   criterion instead of overbuilding a gate. Keep this: it is more useful than a
   spotless-looking task list.

## Watch-for

1. **For every new public claim, ask for its evidence anchor, surface list, and
   drift guard before accepting the wording.** This is Pattern 1 applied to any
   README/site/npm/marketplace promise, not only support tiers.

2. **When adding a supported agent, treat the validation record as the feature,
   not paperwork.** It must state channel, model, effort, scenario limits, audit
   result, and interview-protocol judgment; if R-035 bites, tighten the
   checklist inside the validation template rather than inventing a separate
   process.

3. **Challenge "MUST" rules that have no structural affordance.** If a skill
   fix relies only on stronger wording, ask what checkpoint, example, test,
   artifact, or harness hook makes the behavior more likely to happen.

4. **Public adoption has begun; keep the deferred triggers live.** Before
   merging the first nontrivial outside contribution, revisit R-002. On the
   first skill-name collision report, revisit R-013. Before team/project-level
   install work, revisit R-025. On first getting-started confusion, revisit
   R-029.

5. **Do not treat "unpublish/drop" as automatically cleaner than "deprecate and
   point."** T-043 was right for a no-user placeholder, but future public
   migration decisions should explicitly price searchability, name squatting,
   and user signposts before dropping the pointer.

6. **Installer/update work needs stale-file semantics.** T-052 surfaced that
   old installed skills can linger after removal from the source set; the next
   installer/update design pass should decide prune, warn, or preserve, rather
   than discovering it through a future clean-machine surprise.
