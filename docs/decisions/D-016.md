## D-016: The installer CLI is native ESM — `"type": "module"`, static imports, named exports

- **Status**: accepted
- **Date**: 2026-07-03
- **Context**: The `cli/` installer — the repo's only JavaScript (D-009 keeps all skill scripts in Python) — was written in CommonJS (`require`/`module.exports`), including lazy per-subcommand `require()` calls in the bin entrypoint. The owner directed a move to ES6+ modules.
- **Decision**: `cli/package.json` gains `"type": "module"`; all files keep their `.js` extensions. `module.exports` objects become named exports; relative imports carry explicit `.js` extensions (ESM requirement). The bin entrypoint uses static top-level imports, replacing the lazy per-subcommand requires. `'use strict'` pragmas are dropped (implicit in ESM). No other style rewrite — the code is already idiomatic ES6+ (const, arrows, template literals).
- **Rationale**: The package is bin-only with no external consumers, so nothing can break on the CJS side, and `"type": "module"` is one line versus `.mjs` extension churn in the bin mapping and imports. Static imports beat dynamic `await import()` here because a ~270-line zero-dependency CLI gains nothing from lazy loading, and parsing the whole import graph on every run fails fast on any conversion error regardless of which subcommand executes.
