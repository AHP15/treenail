## D-025: Anchor maintenance has two modes — repoint moved targets, pin abolished ones to git history

- **Status**: accepted
- **Date**: 2026-07-04
- **Context**: D-024 made Evidence anchors live pointers repointed to "the equivalent new path/string", assuming every moved target has one. Name-bearing anchors don't: T-004's `grep:"name": "keel-skills" in cli/package.json` evidences a fact the rename abolishes outright — repointing it to `"name": "treenail"` would put Evidence proving a treenail package under prose titled "Publish a placeholder keel-skills", the exact history rewriting the policy forbids (R-023). T-018 and T-020 share the shape.
- **Decision**: All of D-024 stands — reservation, hard cutover, immutable prose — with anchor maintenance refined into two explicit modes, both applied in the same edit that touches the target. **Moved** (the evidenced fact persists under a new path/string): repoint to the equivalent, per D-024. **Abolished** (the evidenced fact ceases to exist in the working tree): pin the anchor to history instead — rewrite it as `git:<short-sha>:<original-anchor>`, where `<short-sha>` is the last commit at which the original anchor resolved; it is machine-resolvable via `git show`/`git grep` at that commit, and audit tooling treats `git:`-prefixed anchors as resolving against the named commit rather than the working tree. Pinning preserves the claim verbatim; it never rewrites what was evidenced.
- **Rationale**: The moved/abolished distinction is the smallest rule that keeps every anchor machine-resolvable without ever changing a record's meaning: moved facts stay checkable in the tree, abolished facts stay checkable in history, and the choice between the two is determined by whether the original claim still has a truthful in-tree witness — not by editor judgment. Git history is already the project's immutable substrate, so pinning adds no new infrastructure.
- **Supersedes**: D-024
