## R-003: Server-side rate-limiting is ineffective on stateless serverless, and fixing it reintroduces the datastore D-006 rejected

- **Severity**: high
- **Likelihood**: medium
- **Disposition**: fix
- **Date**: 2026-07-05
- **Date resolved**: 2026-07-05
- **Description**: D-007's "server-side rate-limit" assumes durable per-client counters, but Vercel form endpoints run as stateless serverless functions: in-process counters do not persist between invocations and are not shared across concurrent instances or regions, so a naive in-memory limiter resets constantly and never actually throttles. Making the limit real requires an external shared store (Vercel KV / Redis / Upstash) keyed by IP — which reintroduces exactly the own-datastore, and the IP retention, that D-006 ("store zero PII itself") was designed to avoid. This is independent of traffic volume: the mechanism as specified is architecturally non-functional even against a single persistent abuser, so day-one protection collapses to the honeypot alone.
- **Disposition rationale**: This is a decision-level contradiction between two accepted decisions (D-007's limiter needs shared state; D-006 forbids an own PII datastore), not a guard-able gap — the named mechanism can't work as written. Resolved by superseding D-007 with a decision that names a working, D-006-consistent mechanism.
- **Action**: Superseded by D-016, which specifies a shared ephemeral store keyed on a salted hash of a truncated client IP with a short TTL — a real cross-instance limiter that holds no durable PII, so D-006 still holds. Removes the failure mode. (Residual privacy-claim accuracy from platform logs/analytics is tracked separately by R-004.) **Recommend `red-team-me` scoped to D-016 before it ships** — the superseding decision is itself unexamined.
- **Related decisions**: D-006, D-007
