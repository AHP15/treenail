## R-017: The server-side Turnstile siteverify call is an unbudgeted third-party dependency in the request path with unspecified fail-open/closed behavior

- **Severity**: medium
- **Likelihood**: medium
- **Disposition**: mitigate
- **Date**: 2026-07-05
- **Date resolved**:
- **Description**: D-017 was minted partly to kill R-012 — the KV/Upstash store as "an unbudgeted dependency in the request path with unspecified fail-open/closed and quota behavior." But server-side Turnstile verification reintroduces exactly that shape: every submission now makes a synchronous call to `challenges.cloudflare.com/turnstile/v0/siteverify`, so Cloudflare's verification endpoint is a hard dependency on the form's critical path. D-017 does not specify what happens when siteverify is slow, rate-limited, or down: fail-closed rejects all legitimate submissions during a Cloudflare incident (forms globally unavailable), while fail-open accepts unverified submissions and lets spam through precisely when the check is degraded. The timeout budget, retry policy, and fail direction are all unspecified — the same gap R-012 named, moved from the KV store to the siteverify call.
- **Disposition rationale**: Unlike R-012's store, the siteverify dependency is intrinsic to D-017's chosen mechanism and can't be designed away — but its fail behavior can be specified, which is all the risk asks. So mitigate by pinning the timeout and fail direction, not fix. Medium/medium: Cloudflare siteverify outages are infrequent, but the unspecified policy is a certainty until closed.
- **Action**: Mitigate by specifying the verification call's failure behavior on the form endpoints: (1) a short, explicit timeout budget on the siteverify request; (2) a deliberate **fail-closed** default — a submission whose token cannot be verified is rejected with a user-facing, retry-able error — chosen because the honeypot still runs and the provider-side caps (R-016 mitigation) bound the cost of the brief unavailability, whereas fail-open would leak spam exactly when verification is degraded; (3) documenting the timeout, fail direction, and the absence of any retry/queue so the behavior is a stated contract, not an accident. Fold into the endpoint verification work (T-013).
- **Related decisions**: D-017
