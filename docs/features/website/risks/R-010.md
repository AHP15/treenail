## R-010: D-016's "hashed truncated IP is not PII" premise is unsound, so it never actually resolves the D-006 tension it was minted to fix

- **Severity**: high
- **Likelihood**: medium
- **Disposition**: fix
- **Date**: 2026-07-05
- **Date resolved**: 2026-07-05
- **Description**: D-016 supersedes D-007 on the strength of one load-bearing claim: that a salted-hash-of-truncated-IP ephemeral counter "is not a PII record, so D-006's zero-PII posture holds without exception." That premise is weak. The input space is tiny — the full IPv4 space is 2^32 and a truncated block far smaller — so a hash of it is brute-force-reversible by anyone who obtains the salt (a stored, long-lived secret), and even a salted hash is *pseudonymous*, which under GDPR is still personal data, not anonymous data. If that reading holds, D-016 has not escaped D-006 at all — it has relabelled the same IP-keyed store the decision claimed to avoid, and the R-003 contradiction it was created to resolve is merely hidden behind a hash. The blast radius is the supersession's whole justification: the "fix" is illusory, and D-006's headline "the site stores zero PII itself" is still false.
- **Disposition rationale**: The defect is in D-016's core premise, not a guard-able gap — no amount of tuning makes a hash of a tiny input space non-reversible or makes pseudonymous data non-personal. The only honest resolution is to stop keying the limiter on a client identifier at all, which is a decision change.
- **Action**: Superseded by D-017, which removes the IP-keyed store entirely and ships honeypot + Cloudflare Turnstile day-one — bot resistance with no client-identifier storage, so D-006 holds cleanly with no reconciliation. Removes the failure mode. **Recommend `red-team-me` scoped to D-017 before it ships** — it introduces a Cloudflare/third-party-script dependency that is itself unexamined.
- **Related decisions**: D-016, D-006
