## R-011: Truncating the IP for privacy coarsens the limiter key, so shared-egress users get throttled for a stranger's submissions

- **Severity**: medium
- **Likelihood**: low
- **Disposition**: fix
- **Date**: 2026-07-05
- **Date resolved**: 2026-07-05
- **Description**: D-016 keys the limiter on a *truncated* client IP specifically to weaken its identifiability — but truncation is exactly what makes the key collide. Users behind carrier-grade NAT (mobile networks), corporate proxies, university networks, or a shared VPN egress all fold into one truncated-IP bucket, so once any one of them submits, the rest are rate-limited for a submission they never made — silently rejecting the developer-behind-a-VPN audience the site is aimed at. The privacy/accuracy tradeoff is inherent and unspecified: the coarser the truncation D-016 needs to satisfy R-010's privacy concern, the more legitimate users one bucket sweeps up. Day-to-day this is rare at launch traffic, but a launch spike (HN/Reddit) that clusters many corporate/VPN visitors in the short TTL window is the concrete trigger where it bites.
- **Disposition rationale**: This failure lives entirely in the truncated-IP key that D-017 removes; with no per-client key there is no bucket to collide, so the failure mode is retired by the same supersession that resolved R-010 rather than needing an independent guard.
- **Action**: Superseded by D-017, which drops IP-keyed rate-limiting for honeypot + Turnstile — no per-client bucketing, so shared-egress users are never throttled for a stranger's submission. Removes the failure mode.
- **Related decisions**: D-016
