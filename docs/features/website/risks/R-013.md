## R-013: The Turnstile client widget is a third-party script that privacy tooling blocks, making the forms unsubmittable for the exact target audience

- **Severity**: medium
- **Likelihood**: high
- **Disposition**: mitigate
- **Date**: 2026-07-05
- **Date resolved**:
- **Description**: D-017 verifies a Cloudflare Turnstile token server-side as a hard gate on the form endpoints, and the token can only be minted by loading Cloudflare's `challenges.cloudflare.com/turnstile/v0/api.js` widget in the browser. The landing page targets the individual developer (D-008) — precisely the audience that runs uBlock Origin, Brave shields, Privacy Badger, NoScript, or corporate proxies that block Cloudflare challenge origins. When the widget script is blocked or fails to load, no token is issued, server verification rejects the submission, and the contact and newsletter forms are silently unsubmittable with no non-Turnstile fallback path. The honeypot alone cannot admit these users because D-017 makes Turnstile verification mandatory, not additive.
- **Disposition rationale**: The choice of Turnstile (D-017) is sound; the gap is that a blocked widget dead-ends the user with no escape. That is a missing guard, not a wrong decision, so mitigate rather than fix — Turnstile stays the protection, but the UI must never leave a legitimate user unable to reach the owner.
- **Action**: Mitigate by (1) detecting widget load/render failure client-side and surfacing an explicit, accessible fallback instead of a silently dead form — for the contact form, always expose the owner's direct email (a `mailto:`) as an alternate path; for the newsletter, expose the hosted-list provider's own hosted signup URL; (2) rendering the Turnstile widget in its managed/non-interactive mode so most users never face an interactive challenge at all; (3) ensuring the submit affordance communicates *why* it is disabled when no token is present, rather than failing on submit. The guard keeps Turnstile mandatory for the API path while guaranteeing no blocked-widget user is dead-ended. Tracked by T-021.
- **Related decisions**: D-017, D-008
