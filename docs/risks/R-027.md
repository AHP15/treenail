## R-027: The CI CLI smoke pins Node 22 while engines allows any >=22, so a break on a newer Node major that users actually run is invisible to CI

- **Severity**: low
- **Likelihood**: medium
- **Disposition**: mitigate
- **Date**: 2026-07-04
- **Date resolved**:
- **Description**: D-019's loader smoke — and the whole CI matrix (ubuntu/macos/windows) — runs `setup-node 22`, but `cli/package.json` `engines` is `>=22` (open-ended) and D-020 only enforces the `>=22` *floor*. Users on Node 23/24/25 are officially supported yet never exercised by CI: the smoke validates the floor and never the ceiling. A future Node major that deprecates or removes an API the CLI's import graph or install/update path depends on (`fs.cpSync`, `spawnSync`, `readline`, `crypto`, `import.meta.dirname` behavior) would break for those users while CI stays green, and D-019's loader smoke — built for ESM-conversion regressions, not runtime-API drift — would not catch it. The gap widens every Node release; the project's own dev machine already runs Node 24, diverging from what CI tests. Complementary to R-016 (the too-*old* Node case, below the floor): this is the untested space *above* the floor.
- **Disposition rationale**: Low severity, medium likelihood, but the mitigation is nearly free — a single CI matrix entry — so exercising the ceiling now beats deferring until a Node-version break reaches a user.
- **Action**: Keep D-019/D-020; add a newer-Node lane to the existing CI matrix (e.g. Node current or latest-LTS alongside the Node 22 floor lane) so the open-ended >=22 engines range is exercised at the ceiling, not just the floor. The loader smoke + installer smoke + _shared test suite run unchanged on the added lane.
- **Related decisions**: D-019
