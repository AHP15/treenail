## R-024: The repoint duty exists only in D-024's prose — no skill or check enforces "in the same edit", so future refactors silently recreate dangling anchors

- **Severity**: low
- **Likelihood**: medium
- **Disposition**: mitigate
- **Date**: 2026-07-04
- **Date resolved**:
- **Description**: D-024 obligates whoever moves an anchor target to repoint the anchor in the same edit, but nothing operationalizes that: `task-brief` verifies anchors only at task-completion write time, `audit-artifacts` runs on cadence and detects dangles only after the fact, and no skill prompt or script mentions repointing at all. An agent refactoring shipped code in a future session has no reason to load D-024, so the first post-rename refactor that moves an anchored file recreates R-022's audit noise — now with the added archaeology of working out, from a stale dangle, which long-merged edit moved the target and what the equivalent repoint should have been.
- **Disposition rationale**: Low severity, but the residual is a recurring tax on every future refactor while the guard is a one-time documentation edit in the file every skill already loads — cheap enough to beat accepting a permanent noise source.
- **Action**: T-041 — encode the anchor-maintenance rule (D-025's moved→repoint / abolished→pin, "in the same edit") in the Evidence/anchors section of the conventions spec, where task-brief and audit-artifacts already look, and add the repair flow to audit guidance: a dangling anchor on a done task is repaired per D-025, not merely reported. Additive prose only — no format change, so R-012's backward-compat constraint is untouched.
- **Related decisions**: D-024, D-025, D-012
